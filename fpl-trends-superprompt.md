# FPL Analytics Platform — Build Specification

You are building `fpl-trends`, a Fantasy Premier League analytics platform for the 2026/27 season. This document is the complete specification. Work through it in phase order. Do not begin a phase until the previous phase's acceptance criteria pass.

---

## 0. Operating principles

Read these first. They constrain every design decision that follows.

**0.1 — The FPL API is a snapshot API, not a history API.** A request to `bootstrap-static` returns current state only. There is no endpoint for "ownership three days ago." `transfers_in_event` resets each gameweek. All trend data must be constructed by snapshotting on a schedule. Data not collected is permanently lost.

**0.2 — Never model FPL points directly.** The scoring function changed for 2026/27 (BPS rebalance) and changed for 2025/26 (defensive contributions introduced). Historical points labels were generated by scoring functions that no longer exist. Model the *underlying events* — minutes, goals, assists, clean sheets, defensive actions, saves, BPS components — then apply the current season's scoring function as a separate deterministic layer. Rule changes must be a config edit, never a retrain.

**0.3 — Point-in-time discipline is enforced in code, not by intention.** Every feature used to predict gameweek N must be computable from information available before the gameweek N deadline. This is asserted programmatically (see 2.5), not left to reviewer diligence.

**0.4 — Two validation tracks with different timelines.** Points prediction is backtestable on historical data. Market/trending signals have no historical analogue at the required granularity and can only be validated forward from the moment the collector starts. Do not conflate them.

**0.5 — Fail loudly on schema drift.** FPL renames and restructures fields between seasons without notice. Validate every ingested payload against a schema. An unexpected field is a warning; a missing expected field is a hard error that halts the run and preserves the raw payload.

**0.6 — Ship nothing user-facing before the model is validated.** There is no public launch until the paper-trade evaluation at Phase 4 passes its criteria.

## 2. Phase 0 — Collector

**Goal:** a scheduled job that snapshots the FPL API and writes an append-only time series. No analysis. No frontend. This phase is urgent — every hour it is not running is trend data that cannot be recovered.

### 2.1 Endpoints and cadence

| Endpoint | Cadence | Notes |
|---|---|---|
| `/api/bootstrap-static/` | Hourly | The workhorse. All players, teams, events. |
| `/api/fixtures/` | Daily; hourly on matchdays | Includes per-match stats after completion |
| `/api/element-summary/{id}/` | Daily, batched | ~700 requests. Throttle to 1 req/sec. |
| `/api/event/{gw}/live/` | Every 5 min during matches | Live points, BPS, defensive contributions |
| `/api/entry/{OWN_ID}/` | Daily | Own team only in this phase |
| `/api/entry/{OWN_ID}/history/` | Post-deadline | |
| `/api/entry/{OWN_ID}/transfers/` | Post-deadline | |
| `/api/entry/{OWN_ID}/event/{gw}/picks/` | Post-deadline | 404s before deadline — expected, not an error |

### 2.2 Client requirements

- Descriptive `User-Agent` including a contact URL. This is an undocumented API used courteously.
- Global rate limit: maximum 1 request per second across all endpoints.
- Exponential backoff with jitter on 429 and 5xx. Maximum 5 retries.
- Never poll during the final 10 minutes before a deadline — that is peak load on FPL's infrastructure.
- Treat 404 on `picks` before a deadline as an expected condition, logged at debug level, not an error.

### 2.3 Storage strategy

Three tiers:

**Raw** — full gzipped JSON payload, filename `{endpoint}_{iso8601_utc}.json.gz`. Rolling 14-day retention. This is insurance against parsing bugs, not a permanent archive.

**Distilled** — append to per-gameweek Parquet, one row per player per snapshot, **only when a value changed since the previous snapshot**. Columns:

```
snapshot_ts, element_id, now_cost, selected_by_percent,
transfers_in_event, transfers_out_event, form, status,
chance_of_playing_next_round, news_added, ep_next
```

This delta-only approach keeps a full season under a few megabytes and is the sole basis of every trending metric.

**Reference** — teams, fixtures, player metadata, position mappings. Rewritten wholesale each run. Small.

### 2.4 Schema validation

Define pydantic models for every payload. Note the known cross-season drift: the `events` array moved from top-level `current_event`/`next_event` integers to per-event `is_current`/`is_next` booleans. Write parsers that handle both.

On validation failure: halt the run, preserve the raw payload, emit a clearly labelled error. Do not silently coerce or skip.

### 2.5 Scheduling

GitHub Actions cron. Two things to know: scheduled workflows are best-effort and can drift 5–15 minutes under load (acceptable for hourly trends, not for live-match polling — use a separate faster-cadence workflow gated on fixture times), and Actions auto-disable after 60 days of repository inactivity, which the collector's own commits prevent.

### 2.6 Acceptance criteria

- [ ] Collector runs hourly and commits distilled Parquet
- [ ] A deliberately malformed payload halts the run with a clear error and preserves the raw file
- [ ] Rate limiting verified: no burst exceeds 1 req/sec
- [ ] 14-day raw retention prunes correctly
- [ ] Distilled Parquet contains only changed rows — verified by asserting row count is far below `players × snapshots`
- [ ] A DuckDB query returns a given player's `selected_by_percent` as of an arbitrary past timestamp

## 3. Phase 1 — Historical backfill and backtest harness

**Goal:** a walk-forward validation harness over prior seasons, with leakage assertions and baseline models. Build this *before* the model, so the model is never evaluated by an untested harness.

### 3.1 Sources

- `vaastav/Fantasy-Premier-League` — per-gameweek player data. Use `data/{season}/gws/merged_gw.csv` and the `understat/` directory. Seasons 2023-24, 2024-25, 2025-26.
- `olbauday/FPL-Core-Insights` — 2026/27 data plus dynamic team Elo ratings aligned to official FPL IDs. Use for the Elo layer rather than building one.
- Understat via `soccerdata` for shot-level xG where finer granularity is needed.

### 3.2 Known data hazards

**The `xP` column is contaminated.** It is scraped from FPL's `ep_this` field after each gameweek ends, and empirically reflects post-match information rather than the pre-deadline value managers actually saw. Drop it entirely. Do not use it as a feature under any transformation.

**Position and team assignments in summary files are often season-final.** Retroactively applying 2026/27's eleven position reclassifications to earlier seasons will silently inflate defender models. Resolve position and club per gameweek, not per season.

**Season-aggregate features are future-peeking.** A player's full-season xG cannot be used to predict gameweek 5.

**Promoted clubs have no prior top-flight data.** For 2026/27 these are Coventry City, Hull City and Ipswich Town. They need a principled prior — Championship-adjusted Elo, or a pooled promoted-club baseline — not a null and not last season's relegated-club average by name.

### 3.3 Leakage assertion framework

Implement `backtest/leakage.py` such that every feature carries a declared `available_at` timestamp. Before any training or evaluation run, assert for every row:

```
feature.available_at < gameweek.deadline_time
```

A violation raises, it does not warn. Include at least three deliberate leakage tests in the suite that must fail loudly.

### 3.4 Baselines

Three benchmarks the model must beat. Implement all three before the model exists.

1. **Trailing mean** — player's mean points over the prior 5 gameweeks.
2. **FPL form** — the `form` field as published pre-deadline.
3. **Fixture-adjusted trailing mean** — baseline 1 scaled by opponent difficulty.

Baseline 3 is the real hurdle. A model that fails to beat it is not earning its complexity.

### 3.5 Walk-forward protocol

Train on gameweeks 1..N, predict N+1, advance, repeat. Never train on data from after the prediction target. Report per-season and pooled.

Metrics: MAE and RMSE on points, Spearman rank correlation within each position, calibration curves, and a decomposition of error by event type (minutes vs goals vs clean sheets vs bonus).

### 3.6 Acceptance criteria

- [ ] Three seasons backfilled and schema-normalized
- [ ] All three baselines implemented with reported metrics
- [ ] Leakage assertions run on every backtest; three deliberate-violation tests fail as expected
- [ ] `xP` column absent from the feature set — enforced by a test
- [ ] Position and club resolved per gameweek, verified against a known mid-season transfer
- [ ] Promoted-club prior documented and implemented
- [ ] Walk-forward harness produces a reproducible report from a single command

## 4. Phase 2 — Event model and scoring layer

**Goal:** per-player projections for the next H gameweeks, built as event predictions plus a deterministic scoring function.

### 4.1 Scoring layer

`analytics/scoring.py` takes an event vector and a scoring config, returns points. Pure function, no I/O, exhaustively unit tested.

The 2026/27 config must encode:

- Defensive contribution points, unchanged from 2025/26
- BPS: one point per **three** clearances, blocks and interceptions (changed from per two)
- BPS: no deduction for being tackled (the previous −1 is removed)
- Goalkeeper saves: flat rate per save, with an additional bonus for close-range saves and a further bonus for big-chance saves
- Chips: two full sets, one per half; first set expires at the gameweek 19 deadline, 13:30 GMT, Saturday 2 January 2027, and does not carry over
- Free transfers: bank up to a maximum of five

Validate the scoring function by replaying a completed historical gameweek under its own season's config and asserting reproduction of official points to the point for at least 95% of players. Investigate every discrepancy before proceeding.

### 4.2 Event model

Predict, per player per gameweek, as separate heads:

- `P(appears)` and expected minutes given appearance — this dominates everything else and deserves the most attention
- Expected goals and assists, from underlying rates adjusted for opponent and home/away
- `P(clean sheet)` at team level, then distributed by position
- Expected defensive contributions, and `P(hitting the threshold)` — this is a threshold event, so model the probability of crossing it, not the mean
- Expected saves for goalkeepers, split by save type given the new BPS treatment
- Expected BPS, and `P(bonus rank 1/2/3)` within each fixture

Minutes prediction is the highest-leverage component and the most common failure point. Rotation risk, injury flags via `status` and `chance_of_playing_next_round`, and fixture congestion all belong here.

### 4.3 Custom fixture difficulty

FPL's built-in FDR is static and coarse. Build a replacement from team Elo ratings and, where available, bookmaker-implied clean-sheet and anytime-goalscorer probabilities. Report both yours and FPL's so the difference is visible.

### 4.4 Acceptance criteria

- [ ] Scoring function reproduces official points for ≥95% of players on a replayed historical gameweek; all discrepancies documented
- [ ] Scoring rules live entirely in config — changing a rule requires no Python edit
- [ ] Model beats all three baselines on pooled walk-forward MAE
- [ ] Model beats fixture-adjusted trailing mean on within-position rank correlation
- [ ] Error decomposition reported by event type
- [ ] Minutes head evaluated separately with its own metrics

## 5. Phase 3 — Squad integration

**Goal:** given a team ID, reconstruct squad state and recommend the highest-value legal move.

### 5.1 Squad reconstruction

The API cannot show a squad before the upcoming deadline without session auth. `/api/entry/{id}/event/{gw}/picks/` 404s until the deadline passes. `/api/my-team/{id}/` requires login and is out of scope.

Therefore reconstruct: take `picks` from the last completed deadline, then apply everything from `/api/entry/{id}/transfers/` with a later timestamp. This is derivation, not lookup. Build it that way.

### 5.2 Free transfer derivation

Free transfers remaining are not exposed by any public endpoint. Derive by walking transfer history and applying: one accrued per gameweek, banking capped at five, reset behaviour on wildcard and free hit taken from the `chips` array in `/api/entry/{id}/history/`.

Implement as a standalone, heavily tested function. Every hit calculation downstream depends on it, and an error here corrupts every recommendation silently.

### 5.3 Price rules

**Selling price is not current price.** On a price rise, only half the profit is banked, rounded down. The `picks` endpoint provides `selling_price` directly — use it. Never compute from `now_cost`.

**Budget for a transfer** is `selling_price(outgoing) + bank`. Not squad value. `last_deadline_value` includes the bench and is not spending power.

### 5.4 The recommender is a solver, not a sort

Formulate as an integer linear program.

**Objective:** maximize projected points scored by the starting XI over horizon H, minus transfer hit costs.

**Constraints:**
- Budget: `selling_price(out) + bank ≥ purchase_price(in)`
- Maximum three players per Premier League club
- Squad composition: 2 GK, 5 DEF, 5 MID, 3 FWD
- Legal formation: 1 GK, minimum 3 DEF, minimum 1 FWD in the XI
- Transfer count, with −4 per transfer beyond free transfers available

**Requirements that follow from the formulation:**

- Value is *marginal*. Upgrading the worst starter has real value; upgrading the fourth bench player has approximately none. The objective is change in XI points, not change in player quality.
- Hits clear their hurdle over horizon H, not over one gameweek. H is a user-facing control and materially changes the answer.
- Optimal XI and bench order are computed weekly from projections and flags. Bench order determines autosub outcomes and is free points most managers leave on the table.
- Club stacking is a variance decision as well as a points decision. Surface concentration explicitly rather than burying it in an expected value.
- Fold effective ownership in, or at minimum flag recommendations that are high-variance against the template. A pure points model will recommend selling a 55%-owned premium for +0.3 expected points, which is a poor trade against the field.

### 5.5 Acceptance criteria

- [ ] Squad reconstruction matches a known post-deadline state exactly
- [ ] Free transfer derivation tested against a full season of own transfer history including chip weeks
- [ ] Selling price used everywhere; a test asserts `now_cost` never reaches the budget calculation
- [ ] Solver never proposes an illegal move — property test over randomized squad states
- [ ] Recommendations for a bench-only upgrade correctly score near zero
- [ ] Horizon control demonstrably changes output
- [ ] Template-risk flag fires on a constructed high-ownership-sale case

## 6. Phase 4 — Paper trade

**Goal:** honest forward evaluation across gameweeks 1–13 before any launch.

### 6.1 Freeze protocol

Before every deadline, write predictions to a timestamped, immutable file: per-player projections, recommended XI, recommended transfers, recommended captain. Commit it. Never edit retroactively. A test asserts no frozen file is modified after its gameweek deadline.

### 6.2 Shadow team

Run two tracks: the real team, and a shadow team that follows the solver's recommendation every week with no human override. Comparing them at gameweek 13 answers the only question that matters — whether the model beats the operator's own judgment.

### 6.3 Evaluate the two levels separately

**Player-level prediction.** Roughly 500 players × 13 gameweeks is 6,500+ observations. That is ample for MAE, rank correlation and per-position calibration. Trust these numbers.

**Squad-level strategy.** Roughly 13 observations, dominated by variance. A genuinely good model can sit at 3M overall rank after 13 gameweeks because one captain blanked twice. Log it, report it, and do **not** overhaul the model on the basis of it. Write this warning into the evaluation report output itself.

### 6.4 Trending signal validation

Market signals — ownership acceleration, transfer velocity, price-change pressure — have no historical analogue at hourly granularity. Gameweek 13 is their *first* evaluation window, not their final one. Report them with explicit wide confidence intervals and do not gate launch on them.

### 6.5 Launch gate

Proceed to Phase 5 only if all hold:

- [ ] Model beats fixture-adjusted trailing mean on live gameweeks 1–13 player-level MAE
- [ ] Within-position rank correlation exceeds all three baselines
- [ ] No leakage assertion fired during the live period
- [ ] Squad reconstruction ran without manual correction for 13 consecutive gameweeks
- [ ] Price-change model reports its hit rate with a stated confidence interval

If the gate fails, extend the paper trade. Do not launch on a failed gate.

## 7. Phase 5 — Frontend

**Goal:** static site, no build step, reading generated JSON.

### 7.1 Architecture

GitHub Actions runs collector and analytics, commits JSON into `site/data/`. GitHub Pages or Cloudflare Pages serves it. Same-origin JSON, so no CORS problem for the analytics half.

The FPL API sends no CORS headers, so arbitrary team-ID lookups need the Cloudflare Worker: forward `/entry/*` and `/leagues-classic/*`, add the CORS header, hold no state. Free tier covers 100k requests per day. Add basic per-IP rate limiting.

### 7.2 Views

- **Trending board** (landing) — largest ownership movers up and down with sparklines, transfer velocity leaderboard
- **Price watch** — predicted risers and fallers with progress-toward-threshold bars and a stated hit rate
- **Player explorer** — sortable projections with the event decomposition visible, not just a single score
- **Fixture ticker** — next six gameweeks using the custom difficulty model, with FPL's own FDR shown alongside for comparison
- **Differential finder** — low ownership filtered against strong underlying numbers
- **My team** — team ID input, squad health, recommended moves with reasoning, chip planner respecting the gameweek 19 expiry
- **Model transparency** — live accuracy against baselines, updated weekly. Non-negotiable. If the model is having a bad month, the site says so.

### 7.3 Display requirements

- Every projection shows its uncertainty, never a bare point estimate
- Every recommendation shows its reasoning, not just its rank
- Timestamp all data with its snapshot time
- Degrade gracefully when the Worker is unavailable — the static analytics must still render

### 7.4 Acceptance criteria

- [ ] Site is static files, no build step
- [ ] Worker proxies successfully and rate-limits per IP
- [ ] Analytics views render with the Worker offline
- [ ] Model transparency page reflects live evaluation output, not hardcoded values
- [ ] Chip planner enforces the gameweek 19 expiry

## 8. Cross-cutting requirements

**Testing.** Every phase ships with tests. The leakage framework, scoring function, free transfer derivation, and solver constraints require the highest coverage — those four are where silent wrongness lives.

**Reproducibility.** Any reported metric regenerates from a single command against committed data.

**Documentation.** Every metric in `analytics/` carries a docstring giving its formula, its inputs, and the timestamp at which those inputs become available.

**Attribution.** The underlying data belongs to fantasy.premierleague.com and understat.com. Cite the historical dataset repositories. Include attribution on the site.

**Honesty in output.** When the model is uncertain, the interface says so. When a recommendation is close to a coin flip, it says that too. The transparency page is a feature, not a liability.
