# FPL Analytics Platform — Build Specification

You are building `fpl-trends`, a Fantasy Premier League analytics platform for the 2026/27 season. This document is the complete specification. Work through it in phase order. Do not begin a phase until the previous phase's acceptance criteria pass.

---

## 0. Operating principles

Read these first. They constrain every design decision that follows.

**0.1 — The FPL API is a snapshot API, not a history API.** A request to `bootstrap-static` returns current state only. There is no endpoint for "ownership three days ago." `transfers_in_event` resets each gameweek. All trend data must be constructed by snapshotting on a schedule. Data not collected is permanently lost.

**0.2 — Never model FPL points directly.** The scoring function changed for 2026/27 (BPS rebalance) and changed for 2025/26 (defensive contributions introduced). Historical points labels were generated by scoring functions that no longer exist. Model the *underlying events* — minutes, goals, assists, clean sheets, defensive actions, saves, BPS components — then apply the current season's scoring function as a separate deterministic layer. Rule changes must be a config edit, never a retrain.

**0.3 — Point-in-time discipline is enforced in code, not by intention.** Every feature used to predict gameweek N must be computable from information available before the gameweek N deadline. This is asserted programmatically (see 2.5), not left to reviewer diligence.

**0.4 — Two validation tracks with different timelines.** Points prediction is backtestable on historical data. Market/trending signals have no historical analogue at the required granularity and can only be validated forward from the moment the collector starts. Do not conflate them.

**0.5 — Fail loudly on schema drift.** FPL renames and restructures fields between seasons without notice. Validate every ingested payload against a schema. An unexpected field is a warning; a missing expected field is a hard error that halts the run and preserves the raw payload.

**0.6 — Ship nothing user-facing before the model is validated.** There is no public launch until the paper-trade evaluation at Phase 4 passes its criteria.

## 2. Phase 0 — Collector

**Goal:** a scheduled job that snapshots the FPL API and writes an append-only time series. No analysis. No frontend. This phase is urgent — every hour it is not running is trend data that cannot be recovered.

### 2.1 Endpoints and cadence

| Endpoint | Cadence | Notes |
|---|---|---|
| `/api/bootstrap-static/` | Hourly | The workhorse. All players, teams, events. |
| `/api/fixtures/` | Daily; hourly on matchdays | Includes per-match stats after completion |
| `/api/element-summary/{id}/` | Daily, batched | ~700 requests. Throttle to 1 req/sec. |
| `/api/event/{gw}/live/` | Every 5 min during matches | Live points, BPS, defensive contributions |
| `/api/entry/{OWN_ID}/` | Daily | Own team only in this phase |
| `/api/entry/{OWN_ID}/history/` | Post-deadline | |
| `/api/entry/{OWN_ID}/transfers/` | Post-deadline | |
| `/api/entry/{OWN_ID}/event/{gw}/picks/` | Post-deadline | 404s before deadline — expected, not an error |

### 2.2 Client requirements

- Descriptive `User-Agent` including a contact URL. This is an undocumented API used courteously.
- Global rate limit: maximum 1 request per second across all endpoints.
- Exponential backoff with jitter on 429 and 5xx. Maximum 5 retries.
- Never poll during the final 10 minutes before a deadline — that is peak load on FPL's infrastructure.
- Treat 404 on `picks` before a deadline as an expected condition, logged at debug level, not an error.

### 2.3 Storage strategy

Three tiers:

**Raw** — full gzipped JSON payload, filename `{endpoint}_{iso8601_utc}.json.gz`. Rolling 14-day retention. This is insurance against parsing bugs, not a permanent archive.

**Distilled** — append to per-gameweek Parquet, one row per player per snapshot, **only when a value changed since the previous snapshot**. Columns:

```
snapshot_ts, element_id, now_cost, selected_by_percent,
transfers_in_event, transfers_out_event, form, status,
chance_of_playing_next_round, news_added, ep_next
```

This delta-only approach keeps a full season under a few megabytes and is the sole basis of every trending metric.

**Reference** — teams, fixtures, player metadata, position mappings. Rewritten wholesale each run. Small.

### 2.4 Schema validation

Define pydantic models for every payload. Note the known cross-season drift: the `events` array moved from top-level `current_event`/`next_event` integers to per-event `is_current`/`is_next` booleans. Write parsers that handle both.

On validation failure: halt the run, preserve the raw payload, emit a clearly labelled error. Do not silently coerce or skip.

### 2.5 Scheduling

GitHub Actions cron. Two things to know: scheduled workflows are best-effort and can drift 5–15 minutes under load (acceptable for hourly trends, not for live-match polling — use a separate faster-cadence workflow gated on fixture times), and Actions auto-disable after 60 days of repository inactivity, which the collector's own commits prevent.

### 2.6 Acceptance criteria

- [ ] Collector runs hourly and commits distilled Parquet
- [ ] A deliberately malformed payload halts the run with a clear error and preserves the raw file
- [ ] Rate limiting verified: no burst exceeds 1 req/sec
- [ ] 14-day raw retention prunes correctly
- [ ] Distilled Parquet contains only changed rows — verified by asserting row count is far below `players × snapshots`
- [ ] A DuckDB query returns a given player's `selected_by_percent` as of an arbitrary past timestamp

## 3. Phase 1 — Historical backfill and backtest harness

**Goal:** a walk-forward validation harness over prior seasons, with leakage assertions and baseline models. Build this *before* the model, so the model is never evaluated by an untested harness.

### 3.1 Sources

- `vaastav/Fantasy-Premier-League` — per-gameweek player data. Use `data/{season}/gws/merged_gw.csv` and the `understat/` directory. Seasons 2023-24, 2024-25, 2025-26.
- `olbauday/FPL-Core-Insights` — 2026/27 data plus dynamic team Elo ratings aligned to official FPL IDs. Use for the Elo layer rather than building one.
- Understat via `soccerdata` for shot-level xG where finer granularity is needed.

### 3.2 Known data hazards

**The `xP` column is contaminated.** It is scraped from FPL's `ep_this` field after each gameweek ends, and empirically reflects post-match information rather than the pre-deadline value managers actually saw. Drop it entirely. Do not use it as a feature under any transformation.

**Position and team assignments in summary files are often season-final.** Retroactively applying 2026/27's eleven position reclassifications to earlier seasons will silently inflate defender models. Resolve position and club per gameweek, not per season.

**Season-aggregate features are future-peeking.** A player's full-season xG cannot be used to predict gameweek 5.

**Promoted clubs have no prior top-flight data.** For 2026/27 these are Coventry City, Hull City and Ipswich Town. They need a principled prior — Championship-adjusted Elo, or a pooled promoted-club baseline — not a null and not last season's relegated-club average by name.

### 3.3 Leakage assertion framework

Implement `backtest/leakage.py` such that every feature carries a declared `available_at` timestamp. Before any training or evaluation run, assert for every row:

```
feature.available_at < gameweek.deadline_time
```

A violation raises, it does not warn. Include at least three deliberate leakage tests in the suite that must fail loudly.

### 3.4 Baselines

Three benchmarks the model must beat. Implement all three before the model exists.

1. **Trailing mean** — player's mean points over the prior 5 gameweeks.
2. **FPL form** — the `form` field as published pre-deadline.
3. **Fixture-adjusted trailing mean** — baseline 1 scaled by opponent difficulty.

Baseline 3 is the real hurdle. A model that fails to beat it is not earning its complexity.

### 3.5 Walk-forward protocol

Train on gameweeks 1..N, predict N+1, advance, repeat. Never train on data from after the prediction target. Report per-season and pooled.

Metrics: MAE and RMSE on points, Spearman rank correlation within each position, calibration curves, and a decomposition of error by event type (minutes vs goals vs clean sheets vs bonus).

### 3.6 Acceptance criteria

- [ ] Three seasons backfilled and schema-normalized
- [ ] All three baselines implemented with reported metrics
- [ ] Leakage assertions run on every backtest; three deliberate-violation tests fail as expected
- [ ] `xP` column absent from the feature set — enforced by a test
- [ ] Position and club resolved per gameweek, verified against a known mid-season transfer
- [ ] Promoted-club prior documented and implemented
- [ ] Walk-forward harness produces a reproducible report from a single command

## 4. Phase 2 — Event model and scoring layer

**Goal:** per-player projections for the next H gameweeks, built as event predictions plus a deterministic scoring function.

### 4.1 Scoring layer

`analytics/scoring.py` takes an event vector and a scoring config, returns points. Pure function, no I/O, exhaustively unit tested.

The 2026/27 config must encode:

- Defensive contribution points, unchanged from 2025/26
- BPS: one point per **three** clearances, blocks and interceptions (changed from per two)
- BPS: no deduction for being tackled (the previous −1 is removed)
- Goalkeeper saves: flat rate per save, with an additional bonus for close-range saves and a further bonus for big-chance saves
- Chips: two full sets, one per half; first set expires at the gameweek 19 deadline, 13:30 GMT, Saturday 2 January 2027, and does not carry over
- Free transfers: bank up to a maximum of five

Validate the scoring function by replaying a completed historical gameweek under its own season's config and asserting reproduction of official points to the point for at least 95% of players. Investigate every discrepancy before proceeding.

### 4.2 Event model

Predict, per player per gameweek, as separate heads:

- `P(appears)` and expected minutes given appearance — this dominates everything else and deserves the most attention
- Expected goals and assists, from underlying rates adjusted for opponent and home/away
- `P(clean sheet)` at team level, then distributed by position
- Expected defensive contributions, and `P(hitting the threshold)` — this is a threshold event, so model the probability of crossing it, not the mean
- Expected saves for goalkeepers, split by save type given the new BPS treatment
- Expected BPS, and `P(bonus rank 1/2/3)` within each fixture

Minutes prediction is the highest-leverage component and the most common failure point. Rotation risk, injury flags via `status` and `chance_of_playing_next_round`, and fixture congestion all belong here.

### 4.3 Custom fixture difficulty

FPL's built-in FDR is static and coarse. Build a replacement from team Elo ratings and, where available, bookmaker-implied clean-sheet and anytime-goalscorer probabilities. Report both yours and FPL's so the difference is visible.

### 4.4 Acceptance criteria

- [ ] Scoring function reproduces official points for ≥95% of players on a replayed historical gameweek; all discrepancies documented
- [ ] Scoring rules live entirely in config — changing a rule requires no Python edit
- [ ] Model beats all three baselines on pooled walk-forward MAE
- [ ] Model beats fixture-adjusted trailing mean on within-position rank correlation
- [ ] Error decomposition reported by event type
- [ ] Minutes head evaluated separately with its own metrics

## 5. Phase 3 — Squad integration

**Goal:** given a team ID, reconstruct squad state and recommend the highest-value legal move.

### 5.1 Squad reconstruction

The API cannot show a squad before the upcoming deadline without session auth. `/api/entry/{id}/event/{gw}/picks/` 404s until the deadline passes. `/api/my-team/{id}/` requires login and is out of scope.

Therefore reconstruct: take `picks` from the last completed deadline, then apply everything from `/api/entry/{id}/transfers/` with a later timestamp. This is derivation, not lookup. Build it that way.

### 5.2 Free transfer derivation

Free transfers remaining are not exposed by any public endpoint. Derive by walking transfer history and applying: one accrued per gameweek, banking capped at five, reset behaviour on wildcard and free hit taken from the `chips` array in `/api/entry/{id}/history/`.

Implement as a standalone, heavily tested function. Every hit calculation downstream depends on it, and an error here corrupts every recommendation silently.

### 5.3 Price rules

**Selling price is not current price.** On a price rise, only half the profit is banked, rounded down. The `picks` endpoint provides `selling_price` directly — use it. Never compute from `now_cost`.

**Budget for a transfer** is `selling_price(outgoing) + bank`. Not squad value. `last_deadline_value` includes the bench and is not spending power.

### 5.4 The recommender is a solver, not a sort

Formulate as an integer linear program.

**Objective:** maximize projected points scored by the starting XI over horizon H, minus transfer hit costs.

**Constraints:**
- Budget: `selling_price(out) + bank ≥ purchase_price(in)`
- Maximum three players per Premier League club
- Squad composition: 2 GK, 5 DEF, 5 MID, 3 FWD
- Legal formation: 1 GK, minimum 3 DEF, minimum 1 FWD in the XI
- Transfer count, with −4 per transfer beyond free transfers available

**Requirements that follow from the formulation:**

- Value is *marginal*. Upgrading the worst starter has real value; upgrading the fourth bench player has approximately none. The objective is change in XI points, not change in player quality.
- Hits clear their hurdle over horizon H, not over one gameweek. H is a user-facing control and materially changes the answer.
- Optimal XI and bench order are computed weekly from projections and flags. Bench order determines autosub outcomes and is free points most managers leave on the table.
- Club stacking is a variance decision as well as a points decision. Surface concentration explicitly rather than burying it in an expected value.
- Fold effective ownership in, or at minimum flag recommendations that are high-variance against the template. A pure points model will recommend selling a 55%-owned premium for +0.3 expected points, which is a poor trade against the field.

### 5.5 Acceptance criteria

- [ ] Squad reconstruction matches a known post-deadline state exactly
- [ ] Free transfer derivation tested against a full season of own transfer history including chip weeks
- [ ] Selling price used everywhere; a test asserts `now_cost` never reaches the budget calculation
- [ ] Solver never proposes an illegal move — property test over randomized squad states
- [ ] Recommendations for a bench-only upgrade correctly score near zero
- [ ] Horizon control demonstrably changes output
- [ ] Template-risk flag fires on a constructed high-ownership-sale case

## 6. Phase 4 — Paper trade

**Goal:** honest forward evaluation across gameweeks 1–13 before any launch.

### 6.1 Freeze protocol

Before every deadline, write predictions to a timestamped, immutable file: per-player projections, recommended XI, recommended transfers, recommended captain. Commit it. Never edit retroactively. A test asserts no frozen file is modified after its gameweek deadline.

### 6.2 Shadow team

Run two tracks: the real team, and a shadow team that follows the solver's recommendation every week with no human override. Comparing them at gameweek 13 answers the only question that matters — whether the model beats the operator's own judgment.

### 6.3 Evaluate the two levels separately

**Player-level prediction.** Roughly 500 players × 13 gameweeks is 6,500+ observations. That is ample for MAE, rank correlation and per-position calibration. Trust these numbers.

**Squad-level strategy.** Roughly 13 observations, dominated by variance. A genuinely good model can sit at 3M overall rank after 13 gameweeks because one captain blanked twice. Log it, report it, and do **not** overhaul the model on the basis of it. Write this warning into the evaluation report output itself.

### 6.4 Trending signal validation

Market signals — ownership acceleration, transfer velocity, price-change pressure — have no historical analogue at hourly granularity. Gameweek 13 is their *first* evaluation window, not their final one. Report them with explicit wide confidence intervals and do not gate launch on them.

### 6.5 Launch gate

Proceed to Phase 5 only if all hold. Reported live as evidence accumulates,
not gated behind a fixed gameweek count first (see the 2026-09-02 progress
log entry) — a criterion reports its real PASS/FAIL/insufficient-data
answer as soon as it has evidence to answer from, however many gameweeks
that is:

- [ ] Model beats fixture-adjusted trailing mean on live player-level MAE
- [ ] Within-position rank correlation exceeds all three baselines
- [ ] No leakage assertion fired during the live period
- [ ] Squad reconstruction ran without manual correction
- [ ] Price-change model reports its hit rate with a stated confidence interval

If the gate fails, extend the paper trade. Do not launch on a failed gate.

## 7. Phase 5 — Frontend

**Goal:** static site, no build step, reading generated JSON.

### 7.1 Architecture

GitHub Actions runs collector and analytics, commits JSON into `site/data/`. GitHub Pages or Cloudflare Pages serves it. Same-origin JSON, so no CORS problem for the analytics half.

The FPL API sends no CORS headers, so arbitrary team-ID lookups need the Cloudflare Worker: forward `/entry/*` and `/leagues-classic/*`, add the CORS header, hold no state. Free tier covers 100k requests per day. Add basic per-IP rate limiting.

### 7.2 Views

- **Trending board** (landing) — largest ownership movers up and down with sparklines, transfer velocity leaderboard
- **Price watch** — predicted risers and fallers with progress-toward-threshold bars and a stated hit rate
- **Player explorer** — sortable projections with the event decomposition visible, not just a single score
- **Fixture ticker** — next six gameweeks using the custom difficulty model, with FPL's own FDR shown alongside for comparison
- **Differential finder** — low ownership filtered against strong underlying numbers
- **My team** — team ID input, squad health, recommended moves with reasoning, chip planner respecting the gameweek 19 expiry
- **Model transparency** — live accuracy against baselines, updated weekly. Non-negotiable. If the model is having a bad month, the site says so.

### 7.3 Display requirements

- Every projection shows its uncertainty, never a bare point estimate
- Every recommendation shows its reasoning, not just its rank
- Timestamp all data with its snapshot time
- Degrade gracefully when the Worker is unavailable — the static analytics must still render

### 7.4 Acceptance criteria

- [ ] Site is static files, no build step
- [ ] Worker proxies successfully and rate-limits per IP
- [ ] Analytics views render with the Worker offline
- [ ] Model transparency page reflects live evaluation output, not hardcoded values
- [ ] Chip planner enforces the gameweek 19 expiry

## 8. Cross-cutting requirements

**Testing.** Every phase ships with tests. The leakage framework, scoring function, free transfer derivation, and solver constraints require the highest coverage — those four are where silent wrongness lives.

**Reproducibility.** Any reported metric regenerates from a single command against committed data.

**Documentation.** Every metric in `analytics/` carries a docstring giving its formula, its inputs, and the timestamp at which those inputs become available.

**Attribution.** The underlying data belongs to fantasy.premierleague.com and understat.com. Cite the historical dataset repositories. Include attribution on the site.

**Honesty in output.** When the model is uncertain, the interface says so. When a recommendation is close to a coin flip, it says that too. The transparency page is a feature, not a liability.

### The two model columns, and a second null result on momentum — 2026-08-23 (later still)

**`clean_sheet_prob` is built** (`analytics/clean_sheet.py`), and the sixteen-metric matrix (§5.15 Q2) is complete for the first time — `correlations.json` went from 455 cells over 14 metrics to 600 over 16.

It is a team quantity throughout, because a clean sheet is a team outcome: attaching a per-player probability would imply eleven different answers to one event. FPL's 60-minute credit is a minutes question and `minutes_reliability` already carries it.

Poisson on goals conceded, `P(CS) = exp(-lambda)`. The assumption was checked, not assumed: at the league mean Poisson gives P(0)=0.2243 against an empirical 0.2303. `lambda` is a product of measured ratios — no optimizer, none of which the locked stack provides — and every exponent was chosen by sweeping Brier score over the archive:

    lambda = shrunk trailing xGC x home/away^0.25 x (opponent trailing xG / league)^0.5
             x (FPL difficulty / 3)^0.5, blended toward head-to-head, x calibration

**Measured: Brier 0.17056 against 0.17727 for the base rate, skill +3.79%**, calibrated across the range (predicted 0.110/0.172/0.219/0.268/0.368 by quintile against actual 0.126/0.181/0.209/0.282/0.355). Real but modest, and it should be read that way — clean sheets are close to a coin weighted by fixture.

Four things worth carrying forward:

- **Shrinkage toward the league mean was the single biggest term**, +0.78% to +2.11% on its own. Early season is when this model is most used and least informed.
- **Every factor needed damping below exponent 1.** The opponent-attack term at full strength *loses* to the constant base rate (0.17430 against 0.17636); at the square root it gains. Each factor is a ratio of two noisy trailing estimates and the raw ratio over-swings lambda.
- **Head-to-head is real**, and was the largest addition after shrinkage (+3.96% to +4.35% on the tuning subset). Prior meetings between two clubs carry information neither side's general form does.
- **FPL's published difficulty beat our own Elo** (+4.23% against +3.79%) *and* it is committed data, where the Elo table derives from the gitignored raw cache. Using Elo would have made a local build and a CI build produce different numbers for the same commit. `web/export/current.py` now carries `opponent_difficulty` through from the reference fixtures so the current season joins the same scale.

**`minutes_reliability` is built** as `features.trailing_minutes_reliability` — `minutes_distribution`'s existing `p_full`, vectorized across the whole panel instead of rebuilt 114 times, so the exported column inherits that head's published Brier (0.1007 over 83,035) rather than becoming a second unvalidated statistic. A test asserts the two agree gameweek by gameweek.

**Momentum has no edge, measured a second time and against a specific brief.** The proposal was: a consistent rise in xG / assists / DefCon / involvements across three games, the model applied through a shorter lens, current season only. Every form of it was tested over 8,753 player-gameweeks, forward outcome = mean points over the next three:

| definition of Rising | n | forward pts | lift |
| --- | --- | --- | --- |
| monotone rise over 3 games | 1450 | 3.156 vs 3.248 | **-0.092** |
| short(3) mean > long(6) mean | 4370 | 3.235 vs 3.230 | +0.005 |
| short(3) **level**, top quartile | 2188 | 3.736 vs 3.065 | **+0.671** |
| monotone rise AND top-quartile level | 366 | 3.855 vs 3.206 | +0.650 |

A consistent three-game rise predicts *slightly worse* forward points, and adding it to the level filter makes that filter worse (0.650 against 0.671) while cutting the population six-fold. Declining behaves the same way in reverse: a monotone fall gives +0.061, the wrong direction, while bottom-quartile level gives -0.701.

**And the shorter lens is the wrong direction.** Top-quartile level on a 3-game window lifts +0.682; on 6 games +0.712; on 10 games **+0.842**. Longer is better, so what the level filter measures is quality, not form.

Adding DefCon to the composite as the brief specified helps DEF marginally (-0.034 to +0.065 in 2025-26) and does not change the conclusion. The edge that exists is concentrated in MID (+1.090) and FWD (+0.562); DEF is near zero (+0.087).

**This is now two independent measurements agreeing** — the earlier trend-slope test (rho 0.01-0.02 at every window and horizon) and this one against a different, stronger definition. `board.json` is still not written, and the shape of §5.4.6 remains the open decision.

### `board.json` — both surfaces, and the weights fitted at last — 2026-08-23 (final)

**Eight of the nine export files exist.** Only `players.json` remains, and only until the first `record-actuals`.

**The board ships a ranked list *and* the three buckets**, over one composite, because they answer different questions and only one of them has measurable edge. Two files that could disagree about the same player would have been the worse choice.

**§5.4.6's position weights are fitted, not adopted.** The spec's illustrative profiles name three columns that do not exist — `creativity_p90` (ICT is dead), `shots_in_box_p90` (in no source this project has), `minutes_stability` (renamed). The replacements live in `config/frontend.yaml:board.position_weights`, derived over 85k player-gameweeks:

- magnitude = |within-position Spearman of the metric's z-score against mean points over the next three gameweeks|
- **sign taken from the registry's `higher_is_better`, not from the data** — `saves_per90` really does correlate *negatively* for GK (rho -0.076, because saves proxy a leaky defence), and a board rewarding a keeper for making fewer saves would not be modelling goalkeeping. It is dropped rather than inverted.
- restricted to metrics the registry calls primary or secondary for that position, which is what keeps goalkeeper tackles (rho -0.097, pure noise) out
- normalised so |weights| sum to 1 within position

**The headline from that fit: `minutes_reliability` is the strongest single predictor in every position** (rho 0.205-0.250, roughly double the next metric). That is §4.2's "this dominates everything else" arriving from the opposite direction, and it lands the week after the column was built. `clean_sheet_prob` is second for GK (0.116), so both new model columns earn their place immediately.

**Bucket accuracy, measured on what ships**, each bucket compared inside the pool it is drawn from:

| bucket | n | forward pts | vs | lift |
| --- | --- | --- | --- | --- |
| optimal | 6187 | 3.311 vs 2.586 | all classified players | **+0.725** |
| declining | 3760 | 2.473 vs 2.617 | other non-optimal | **-0.144** |
| rising | 1775 | 2.516 vs 2.594 | other non-optimal | -0.077 |

The comparison pool matters and getting it wrong was a real bug in the first version: Optimal takes the top quartile, so scoring a momentum bucket against "everyone else" scores it against a pool the good players were already removed from. It read as -0.287 for Rising before the fix and -0.077 after.

**Declining survives; Rising does not.** A flagged declining player really does score less than his non-optimal peers, and for a *warning* that is the right sign. Rising still points the wrong way across every definition tried. The asymmetry is worth keeping on screen rather than averaging away: the model can see a player falling off and cannot see one arriving.

A second real bug found by looking at the output rather than the tests: `rank` and `percentile` were computed over the whole position *across all history*, so the top goalkeeper came out as rank 245. Both are now computed within (season, gw, position), which is what a board means.

`bucket_accuracy` travels inside `board.json` rather than beside it, so a surface cannot render Rising without being able to render what it is worth — which is §5.4.6's own requirement ("if the app is going to classify players as rising, it must report how often rising players subsequently outperformed") turned into a structural guarantee rather than a promise.

`players.json` was called date-blocked in an earlier entry and that was wrong. - **Season-to-date actuals were reading the latest gameweek for two columns.** The panel carries `minutes` and `total_points` of its own, for the single gameweek each row describes, so an unprefixed join kept the panel's values for exactly those two and the season's for everything else. **The committed exports are served from `data/web/v1/`, never copied into `public/`.** A second copy of every number in the repository is a second thing to go stale. A ~30-line Vite plugin serves them from disk in dev and copies the JSON once at build; the parquet files are deliberately excluded, because §5.3.4 does not commit them and §5.14.8 requires the parquet-backed routes to show their empty state rather than an error.

**Deviation from §5.8.2's v2 orientation rule, recorded per §5.16.** That rule swaps the diverging poles for a metric where low is good, so one scale means "far from the middle" across every heat map. It does not apply to the correlation matrix, and applying it would be a defect: a correlation is symmetric, so orienting a cell by one of its two metrics paints (xGC, xG) and (xG, xGC) in opposing colours for the same rho. The rule is written for heat maps whose cells are metric *values* — Form Matrix and Comparison, milestone 5D — where "high is good" is a property of the cell. Here rho carries its own sign and the legend states what the poles mean. A test asserts the matrix is symmetric.

That was found by a test I had written wrongly: it asserted the orientation rule applied, failed, and the failure turned out to be in the design rather than in the assertion.

**A real accessibility bug the tests caught.** The initial keyboard focus sat at cell (0,0), which is on the diagonal — and the diagonal is not a cell, because a metric's correlation with itself is 1 by construction and the export omits it. So the grid had no keyboard entry point at all. Focus now starts on the first real cell, and arrow keys step *over* the diagonal in the direction of travel rather than stalling on it.

Craft rules from §5.8.8 that are implemented rather than noted: OKLCH tokens with an sRGB `@supports` fallback, `color-mix(in oklch)` for the ramp so equal steps in rho read as equal visual steps, a six-step 4px spacing scale, `clamp()` type at 1.2 for data and 1.333 for display, zero radius on data surfaces and 4px on controls only, 28px matrix cells, hairlines at 0.5px above 2dppx, two motion durations and one easing with the whole reveal disabled under `prefers-reduced-motion`, container queries rather than viewport media queries, designed `:focus-visible` and no `outline: none` anywhere.

Amber appears exactly twice in the view, both times as an epistemic warning per §5.8.2: the §5.7.5 mixed-position caution on the pooled group, and the legend's statement of how many cells are hatched. The hatch itself is a `repeating-linear-gradient` rather than a colour, so §5.10's "no heat map encodes meaning by colour alone" survives greyscale and a screenshot.

Loading is a determinate bar with a real byte count read off the response stream — §5.9 wants the user to know whether they are waiting on 200 KB or 8 MB, and §5.8.8 forbids skeletons because they imply content shape before it is known.

### Season selection, and §5.6.1's exception is now live — 2026-08-23

The reader can choose which seasons the Spearman runs over. That is the
first feature to need §5.6.1's client-side exception, and it is the reason

**Why it cannot be precomputed.** Spearman does not compose: rho over

The user can now ask their own questions. Four drop zones over the panel,

**The app has a shell.** `main.tsx` rendered `CorrelationLab` directly

Phase 3/4 entries §5.1.3 requires as disabled explanations rather than

misrepresents the shape of the tool, and one that links them to a blank
page misrepresents its progress.

**URL is state, from the start rather than retrofitted (§5.5).** The full
encoding, the filter bar, the position filter, the toggle and the player

checks the round trip over generated states rather than checking the
format. State changes `replaceState`; only navigation pushes — dragging a
column through four zones should not cost four presses of the back

**Mark inference is the §5.4.2 table and nothing else.** Transcribed row

**DuckDB groups; TypeScript reduces.** This is the load-bearing decision
of the milestone and it is not what §5.1.2's layer diagram implies. §5.6.2
lets the browser reduce on the grounds that its seven operations "cannot
silently disagree with Python because there is nothing to disagree
about" — which is only true if there is exactly **one** implementation and
a golden test holds it against Python. So the SQL in `query/panel.ts`
filters, groups, and `list(...)`s the values out, and `query/reduce.ts`
does the arithmetic in plain TypeScript. Writing `avg(x)` in SQL would
have been shorter and would have left the numbers on screen covered by no
test that runs in CI. A guard test now forbids an aggregate appearing

to work. Sampled from **2023-24 and 2024-25 only**, so `cbi_per90` is
absent from every row rather than merely sparse, which is what puts the
empty-set rule under test with real absence instead of a constructed
blank. `quantile` is pinned to linear interpolation and `sum` adds in
ascending order, both because they are the only places these seven names
admit a choice at all.

**The silent bug this milestone nearly shipped.** Arrow's
`Vector.toArray()` hands back the underlying typed array and **ignores the
validity bitmap**. Measured on one gameweek of `xg_per90`: 309 of 616
values are null, and `toArray()` returned `2.5465051432e-313` and
`1.9e-322` for them — uninitialised memory, as Float64, silently. Those
would not have looked like an error. They would have looked like a player
with a very small xG, averaged into a mean, and drawn. `normalizeList`
now iterates the vector, which reads the bitmap and yields real nulls; it
is slower and it is the only correct option. §5.3.3 arriving from an

Bars did not start from zero, so a mean xGI of 1.20 drew about ten times

tool §5.0.1 calls a diagnostic instrument. Bar and histogram scales now
include zero; point and line keep a fitted scale, because they encode by
position and forcing zero on a rate between 0.4 and 1.2 flattens every
real difference into the top fifth of the plot. Separately, twenty team
names on one axis collided into illegibility; long category labels now
rotate and the plot area sizes itself for them, rather than thinning
labels the reader is scanning for.

**Deviations recorded per §5.16:**

**D6. `temporal | quantitative | any` is implemented as "any *categorical*
colour."** A quantitative colour cannot split a line into series, and the
alternatives — binning it, or running a gradient along the path — are an
estimator choice and a decoration respectively. The reason string names
the fix.

**D7. Rows the §5.4.2 table writes with `—` in the Colour column require
that zone to be empty.** A drop zone that accepts a column and then does
nothing with it is worse than one that says why it cannot.

**D8. Series colour samples the diverging ramp rather than a categorical
palette.** §5.8.2 defines none, and inventing one would spend the visual
budget §5.8.5 explicitly assigns elsewhere. It is a real if small
distortion — an ordered ramp on unordered categories implies a sequence
that is not there — mitigated by colour never being the only encoding:
every series carries a dash pattern and a legend entry, so the chart

**D9. `golden_reductions.json` is an eleventh export file**, alongside
`observations.json`'s tenth. §5.2.1's module list names no module for it,
exactly as it names none for `golden.py`, and it lives beside its sibling

**D10. DuckDB-WASM is gone, and §5.2's locked stack is amended.** It was
built on DuckDB first, and the engine chunk missed §5.9's 1.2 MB budget

What made the swap cheap is that the engine had already stopped doing the

### Future-proofing: 2026-27 is a filter option before its data exists — 2026-08-23

### The archive bias, found and corrected — 2026-08-24

The operator's read was right, and the sharpest evidence was sitting in
the export directory the whole time: **`fixtures.json` was read by
nothing but a contract test.**

Every surface in the app reads player history. `fixtures.json` is one of
§5.3.2's own exported files, it carries the whole 2026-27 schedule with
both difficulty ratings, it is committed, schema'd and contract-tested —
and no view had ever opened it. A model output (`analytics/fdr.py`'s Elo
difficulty, built in Phase 2) had no screen at all.

The bias underneath it is structural rather than accidental. The panel,
`players.json` and `board.json` are all keyed to *the last gameweek the
panel holds*, which is by construction the last one that finished. The
Correlation Lab pools player-seasons. The Scorecard is a backtest. Every
one of the eight surfaces describes gameweeks that are over, and the app
had no way even to name the week the reader is in.

**D13, recorded per §5.16: a ninth surface.** §5.4 says "Eight", so this
is a deviation and not a reading of the spec. The Fixture Ticker shows
every club by gameweek, coloured by difficulty, ranked by the run each
faces, with blanks and doubles read from the schedule and played fixtures
dimmed. It stays inside §5.0.2 by ranking *clubs* on a schedule rather
than suggesting a transfer or naming a captain.

It also matters in a way none of the eight can right now: until the
collector records the first current-season gameweek, every player-keyed
surface *necessarily* describes 2025-26. Clubs are known for 2026-27
today, so this is the one thing in the app that can be about the season
being played before any of it has been.

**Both difficulty ratings are switchable, and they disagree.** FPL's
published 1-5 puts Newcastle, Coventry and Everton on the kindest opening
runs; the Elo rating puts Arsenal, Man City and Man Utd there. The panel
uses FPL's for the clean-sheet model — measured better, and committed
data — but that argument is about what to build a projection on, not
about what a reader may look at. Switching the basis re-ranks the table,
which is a bug that was caught and fixed mid-build: the first version
recoloured the cells by Elo while still ranking the rows by FPL, showing
two opinions in one table under one label.

**Two required spec items were missing, and both were current-season
features.**

§5.4.5 lists "next-N fixture difficulty" among the Explorer's column
groups. It did not exist. It does now — the next five fixtures plus the
mean over them, sortable, which is the column anyone actually sorts by.

§5.4.3 asks the Form Matrix for blank markers. It had only doubles, from
`n_fixtures`. A blank leaves no row at all, so the panel alone cannot
tell "the club had no fixture" from "this player was not in the squad" —
two facts a reader draws opposite conclusions from. With the schedule it
can, and `cellState` now returns five states rather than four.
TypeScript caught the two non-exhaustive switches the moment the union
grew, which is what the discriminated union is for.

**The season guard is the load-bearing safety property.** `fixtures.json`
describes one season. Applying its schedule to a 2024-25 row would invent
blanks and doubles that never happened, silently, in a grid that would
render perfectly. Every helper in `data/fixtures.ts` takes the season
being displayed and returns nothing when it does not match, so an archive
season gets no annotations rather than wrong ones — and fourteen tests
hold that, including one asserting each archive season gets an empty
schedule.

That guard is why the Explorer's new columns are dark today:
`players.json` still describes 2025-26 while the schedule describes
2026-27, and attributing a 2026-27 run to a player through his 2025-26
club would be quietly wrong for anyone who moved. They light up when the
panel carries the current season.

**Also corrected: the app was projecting gameweek 39.** `players.json`
computes `gameweek + 1`, which is right all season and runs off the end
once the last gameweek is recorded — so Comparison read "projecting 39"
of a 38-week season. The number is still meaningful (a fixture-neutral
expectation per appearance); the label was not. It now says the season is
complete and what the number therefore is.

### Key deviations from the literal spec text (all deliberate, all documented in-code and in README.md — read those docstrings before "fixing" any of these)

1. **Two extra dependencies beyond §1.1's locked stack**: `pyyaml` (parses the mandated `config/*.yaml` files — nothing in the locked list does), `pytz` and `tzdata` (duckdb/polars/Windows zoneinfo needs). All justified at their import sites.
2. **Raw tier (`data/raw/`) is gitignored**, not committed — insurance, not archive, per §2.3's own framing. Uploaded as a 14-day GitHub Actions artifact instead (see `collect.yml`).
3. **`data/historical/{season}.parquet` IS committed** (unlike raw data) — §8's reproducibility requirement means the backtest can't depend on `vaastav/Fantasy-Premier-League` staying up. Only `data/historical/raw/` (the downloaded CSV cache) is gitignored.
4. **Double gameweeks are summed, not rejected**: real data (2023-24 gw7 alone: 983 rows) has rearranged fixtures giving one player two matches in one FPL round. `backtest/backfill.py` sums per-fixture stats the way FPL sums a manager's week.
5. **`position == "AM"` rows excluded**: FPL's short-lived "Assistant Manager" pick (2024-25 round 23+) — real head coaches scored by team results, not players. Found during scoring validation, not anticipated.
6. **Elo is self-built** (`analytics/fdr.py`), not sourced from `olbauday/FPL-Core-Insights` as §3.1 suggests — that repo only has genuine per-gameweek dynamic Elo for one of the three backtest seasons (2025-26); the other two are single static end-of-season snapshots that would leak final-season strength into early-gameweek predictions. Point-in-time discipline (§0.3) won out over the literal sourcing suggestion.
7. **Full BPS reproduction is out of scope** — FPL has never published the complete formula/weights. `bonus` is used as a direct input to `compute_points` (already correct in the historical data) rather than re-derived from a BPS-ranking-within-fixture simulation. `analytics/scoring.py:compute_bps` is an illustrative, documented-as-approximate reconstruction that exists only to make the two BPS rule deltas §4.1 names (CBI divisor, tackled deduction) config-driven and testable.
8. **2026/27 GK save-bonus point values are provisional** (`config/scoring_2026_27.yaml`) — the rule change is documented in §4.1 but no exact values are published anywhere, and there's no completed 2026/27 gameweek yet to validate against (the season's first deadline was gw1, 2026-08-21 — the same day Phase 0 went live). Change the config, not the code, once real values are known.
9. **2023-24 reuses `config/scoring_2024_25.yaml`** — no scoring rule differs between the two seasons, and §1.2's file layout doesn't call for a separate 2023-24 file.
10. **`GOALS_CONCEDED_SHRINKAGE = 0.7`** in `analytics/projections.py` — not arbitrary tuning. An ablation showed the goals-conceded penalty term, at full weight, pulled within-position Spearman below the baseline it needs to beat (concentrated in DEF) despite improving MAE; at zero weight the reverse. 0.6-0.85 is a wide, robust plateau clearing both bars; 0.7 is the middle of it. If Phase 3+ work touches `projections.py`, don't "clean up" this constant without rerunning `uv run python -m analytics evaluate` to confirm both bars still clear.

11. **§6.1's immutability rule is "exactly one commit *since the path's most recent deletion*"**, not the literal "exactly one commit" (`papertrade/freeze.py:git_commit_times`). A premature freeze must be retirable — gw2's was written seven days early and had to go — and a rule counting a retirement against its replacement would force known-degenerate data to be kept in order to stay green. The guarantee the rule actually protects is unchanged: the file that currently sits at that path was written once, before its deadline, and never edited.
12. **`assert_immutable_in_git` runs over the real `papertrade/freezes/` directory** in `tests/test_freeze.py`, and skips while that directory is empty. An uncommitted freeze is skipped rather than failed — immutability is a claim about git history, and `write_freeze`'s refusal to overwrite is what guards a file before it is committed.

**(a) §5.4.6's Rising and Declining buckets have no measurable edge.** The spec asserts Rising "is the bucket with real edge: the model's claim is that the process has improved before the output has." Metric *level* does carry signal — rho 0.14 to 0.28 pooled, 0.366 for MID.

§5.4.6 requires the board to publish its own hit rate, §5.4.7 gives that a permanent panel, and §5.14.14 forbids shipping placeholder data, so "build it and see" is not available. The options are: keep the board as a level-based ranking and drop the slope buckets; ship all three buckets with the measured null result displayed on the accuracy panel; or defer the board. It also blocks "Explain this", and §5.13 forbids shipping 5E without that bridge.

**(b) Two of the sixteen matrix metrics do not exist yet, and both appear in §5.4.6's weight profiles.** `clean_sheet_prob` and `minutes_reliability` are registered in `columns.py` as `source: "model"` and are not computed, so `correlations.json` covers fourteen metrics rather than sixteen and the GK/DEF weight profiles reference columns that are absent.

The only open question is whether the panel's trailing window includes the row's own gameweek (descriptive) or stops before it (point-in-time).

`clean_sheet_prob` is **not** cheap and should not be improvised: it needs a team-level Poisson (P(0 goals) from a trailing expected-goals-conceded rate) plus decisions about the window, the home/away adjustment, and whether fixture difficulty enters. **The decision that should be made before milestone 5B, not at 5E:**

The Model Board's Rising/Declining buckets have **no measurable edge**. Measured over the panel: trend-slope ρ is 0.01–0.02 at every window (3–10) and horizon (1–8); the divergence definition (high underlying, low recent points) predicts *worse* forward points at ρ ≈ −0.04 pooled and −0.12 for DEF, because recent points carry role information (penalties, set pieces) that xGI does not see. Metric *level* does carry signal — ρ 0.14→0.28 pooled, 0.366 for MID.

Frontend §5.4.6 requires the board to publish its own hit rate, §5.4.7 gives that a permanent panel, and §5.14.14 forbids shipping placeholder data — so "build it and see" is not available. The options are: drop the buckets and keep the board as a level-based ranking, ship them with the measured null result displayed, or defer the board entirely. It blocks `board.py`, the board-accuracy panel, and "Explain this" — and §5.13 forbids shipping 5E without that bridge. Settle it before the design system is built around a surface that may not exist.

**On Phase 5 and the §6.5 launch gate.** §6.5 says "proceed to Phase 5 only if all hold", and the gate needs gw1–13 — roughly late November. Phase 5A is being built now regardless, and that is not a contradiction: 5A is explicitly "no UI", and frontend §5.1.3 and §5.13 both plan for Phase 3/4 surfaces to stay stubbed *throughout* the frontend build. **The gate blocks launch, not building.** §0.6 says the same thing in the operating principles: nothing user-facing ships before the paper trade passes. Do not read §6.5 as a reason to stop 5A/5B work, and do not read 5A/5B progress as the gate having been met.

### Paper Trade Results ships real, and the Squad Optimizer stays scoped — 2026-08-25

The operator asked for the frontend side of Phase 3 and 4. Both surfaces were `out_of_phase` stubs per §5.1.3/§5.13's "stay stubbed throughout" — and the two turned out not to be the same kind of gap.

**D14, recorded per §5.16: Paper Trade Results ships real in Phase 5.** `papertrade.json` (`web/export/papertrade.py`, `PaperTradeFile` in `contract.py`) exports §6.3–6.5's live evaluation — the shadow team's realized points against the real entry, player-level accuracy per evaluated gameweek, and the §6.5 launch gate's five criteria — and `views/PaperTradeResults.tsx` renders it, replacing the stub. Nothing here decides a transfer, names a captain, or proposes a squad, so it stays inside §5.0.2's Job 1/Job 2 line without redrawing it.

It is **not walled off (§5.8.6)**. Model Board sits on `--panel` with a left rule because it is the model actively classifying players right now; this page sits flat on `--ground`, styled after Scorecard, because it is a report of settled fact, not a live opinion.

The one new thing this surface has to get right that no other export does is **two shas in one file**: `header.model_git_sha` is the code that ran the export, today; each row of `launch_gate.freeze_provenance` carries *that gameweek's own* sha, from when its freeze was written. `PaperTradeResults.tsx` labels them separately rather than implying one number.

Real state as of this writing, confirmed by the export's own first run: `papertrade/freezes/` is empty, `data/current_season/` doesn't exist, and `python -m web.export papertrade` writes the honest zero-gameweek file — `ready_to_launch: false`, four of five criteria "insufficient data", and the fifth (`price_change_model_reports_hit_rate_with_ci`) already computed and **FAIL** at `hit_rate=0.00` over 576 predicted moves of 609 evaluated, which is real live output from `analytics/price_model.py` against today's distilled history, not a placeholder. `tests/test_export_papertrade.py` pins this empty state, one real evaluated gameweek, degenerate-freeze exclusion at both levels, the two-sha distinction, and a NaN-producing MAE serializing as `null`. 6 new Python tests, 6 new frontend tests (`criterionTone`'s three-bucket collapse of the five real status strings), 529 Python tests and 170 frontend tests passing overall. `.github/workflows/papertrade.yml` runs the export right after `freeze`, deliberately outside `web.export all` — every other exporter in `all` is a pure local-file transform, and this one makes a live call to `/entry/{id}/history/` that shouldn't be able to take `board`/`players`/`observations` down with it on a transient failure.

**The Squad Optimizer stays a stub, and this is not the same kind of gap.** Where Paper Trade reports settled history, §5.4's Squad Optimizer answers a live, per-user question — given an arbitrary budget and *this* squad, solve. `squad/optimize.py` already does this (an ILP via `pulp`/CBC), but only for the one shadow-team recommendation `papertrade freeze` computes on a schedule; there is no cached or precomputed path for an arbitrary entry's live squad, and none is possible without either a backend or a browser-side solve. Both fail a hard rule rather than a soft preference: §5.1.1 is "no API server, no database connection from the browser, no runtime Python", and §5.6 forbids inference in the browser outright — an ILP solve *is* the inference, not a reduction of one. A real backend service is the only way to keep the solve server-side; it needs hosting, auth, and uptime this repo has none of, and is a bigger architectural addition than any deviation recorded so far (D10 swapped a library; this would add an operational surface). A client-side WASM/JS port has no precedent here either — D10 rejected DuckDB-WASM on budget grounds for a much lighter job than a MIP solver, and porting one would be a substantial, unproven build. The one option that fits the static architecture — exporting the shadow team's own already-computed `shadow_recommendation` (transfers, captain, bench) as a further Paper Trade Results panel — is not a squad optimizer at all: it answers "what did the automated shadow team do", never "what should *my* squad do", and shipping it under the Phase 3 label would misrepresent it. Recorded here rather than built: don't start 1 or 2 without an explicit operator decision to add a backend or a browser-side solver to the architecture, and treat 3 as a possible small extension to D14 if wanted, labelled as what it is.

`surfaces.ts`'s `optimizer` entry is untouched — still `out_of_phase`/`"Phase 3"`. `papertrade`'s entry is now `live`/`"5G"`.

### The Squad Optimizer stops being a stub: a backend, deliberately — 2026-09-02

The 2026-08-25 entry above recorded the decision, in detail, to leave the Squad Optimizer `out_of_phase` "until an operator explicitly chooses to add a backend or a browser-side solver to the architecture" — the ILP solve in `squad/optimize.py` is inference, not a reduction of one, and frontend §5.1.1/§5.6 rule both a client-side solve and a server dependency out for the rest of the app. Asked directly this session — *"well lets make the backend for it"* — that operator decision is now made, in the direction the log flagged as the one that "keeps the solve server-side": a small FastAPI service, not a browser port.

**`service/app.py`** is the whole of it: a thin HTTP wrapper around the exact path `squad/__main__.py recommend` already exercises live (`squad/live.py:fetch_live_data` → `squad/optimize.py:optimize_squad`), with no logic added beyond what a public, unauthenticated endpoint over a live solve needs and didn't have before — Pydantic request validation (entry id, a horizon capped at 6 gameweeks so an unbounded list can't blow up the ILP's variable count), a per-IP in-memory rate limiter (6 requests/60s, the same "basic per-IP rate limiting" §7.1 already asks for on the Worker, applied here for the identical reason: an endpoint that fans out to the live FPL API on every call), and a mapping from `squad/live.py`'s and `collector/client.py`'s own exceptions to HTTP status — `FPLNotFoundError` → 404, `FPLServerError`/`httpx.TransportError` → 502, `fetch_live_data`'s documented `RuntimeError`s (no gameweek history yet) → 422, anything unanticipated → 500 with the internal message *not* echoed to the caller (`test_unexpected_error_maps_to_500_without_leaking_internals` pins that). `squad/live.py` gained one small extraction, `live_data_caveat(live)` — the early-season data-quality caveat `squad/__main__.py:format_report` already built inline, now shared so the CLI and the HTTP response describe identical `LiveData` with identical words rather than two hand-maintained copies drifting apart.

**Verified against the live API, not just mocked tests.** `uv run uvicorn service.app:app` locally, then a real `POST /api/recommend` for entry 2986528 (the operator's own, already in `config/collector.yaml`) returned a 200 with real transfer recommendations, sourced from `data_gw: 2` — the same live entry `squad/__main__.py` was run against in the 2026-08-21/23 entries above, now reachable over HTTP. `tests/test_service.py` (14 tests) covers the parts a live call can't repeat on every CI run: status-code mapping for each exception type, the rate limiter's ceiling and its per-IP keying, request validation rejecting a bad entry id or an out-of-range/over-length horizon before any solve runs, and `shape_response`'s pairing/captain-marking/position-ordering logic exercised directly against real `squad.optimize` types rather than a canned dict.

**Deployment is Docker, not a specific host.** `Dockerfile` (repo root) is `python:3.12-slim`, not alpine — `pulp`'s bundled CBC binary is a glibc build and would silently fail to run under musl. `render.yaml` targets Render's free tier as one concrete option (zero extra infra beyond the Dockerfile), documented as one among several — Fly.io or Railway would build the identical image. **Not deployed from this session**: no hosting account, no secrets, and provisioning one is the user's call to make, not this session's to make for them — `render.yaml`'s `ALLOWED_ORIGINS: "*"` default is deliberately permissive so a first deploy succeeds with zero configuration, and the README section says explicitly to tighten it to the real frontend origin afterward. The Docker build itself is also unverified end-to-end (no Docker available in this environment to run it) — the pulp+CBC-on-slim combination is a well-worn pattern, but that specific risk is unverified and worth checking on the first real deploy.

**The frontend surface, D15 (§5.16): the Squad Optimizer ships live in Phase 5, the same category of deviation as Paper Trade Results' D14** — except this one *does* cross the Job 1/Job 2 line §5.0.2 draws, deliberately: unlike D14's "reports settled fact", this surface takes a team ID and proposes a transfer, which is exactly what a Phase 3 surface does.
